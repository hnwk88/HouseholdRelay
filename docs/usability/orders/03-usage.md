# 易用性 3/4：个人用量、持久化查询与 40 天清理

## 目标与前置

前置：同批次“易用性 2/4：账户/API 直接配置、可信 HTTPS 与统一调用”已验收。按 `docs/usability/ASSESSMENT.md` 第 6 节的用量合同实施，让每人的请求数、输入/输出 Token 和缺失情况能在网页查询并跨重启保存。两种上游模式采用相同统计合同。

## 必须实施

1. 在鉴权后的受支持请求进入转发前持久化起始记录，使用唯一 request_id，关联稳定 user_id、token_id、上游版本、UTC 开始时间、接口类别和模型。按结束结果幂等更新；不从姓名、metadata 或客户端申报字段推断使用者。
2. 分别统计推理、估算、模型查询及成功/失败/取消；管理诊断、健康检查、静态页面、HEAD 预热和无法鉴权的流量不计入个人模型消耗。鉴权后未发往上游的拒绝记录为该人失败，明确“未发送”。
3. 解析 JSON usage 和 SSE message_start/message_delta。流式累计值采用更新语义，不求和；缓存读/写用量存在时单列。支持网络任意分片、UTF-8 分片、未知事件和有界解析内存，不缓存整个流式回答、不破坏及时刷新。
4. Token 列可空，保存完整/部分/上游未提供/不适用状态。没有最终事件、缺失 usage、取消或中断时不能写零冒充完整用量；保留部分已知值。页面显示已知合计及未知/不完整请求数，全部未知时显示未知；count_tokens 估算与实际消耗分开。
5. 管理员按使用者、时间、接口、模型和结果查询/汇总；个人入口只能查询自己的数据，不接受客户端自行指定其他人 ID。轮换令牌和改名不切断历史归属；停用令牌不能查询或调用。
6. 持久化不得持有贯穿网络请求的事务。起始写入失败时不向上游发送；结束写入独立于请求取消并有界重试、可见失败。启动恢复未完成记录为中断/用量不完整，正常重启完整保留已结束结果，不静默丢记录。
7. 默认 40×24 小时滚动窗口，按 request_started_at UTC 严格小于截止时间清理，边界等于时保留；启动清理及至少每小时清理。查询始终过滤窗口，明细与持久化汇总一致；配置、使用者及令牌不被清理。显示本地时间但不按本地午夜删除。
8. 用量数据库不保存提示词、回答内容或凭据。增加必要索引、分页、清理批次和并发压力验证，确保小部署长时间使用不会因每次查询全表扫描或逐条提交明显阻塞转发。

## 验收证据

- 甲乙并发请求使用不同已知用量，分别正确归属；轮换后继续归原人，改名不改变历史，伪造 user_id 请求无效，个人无法读到他人用量。
- JSON 完整/缺失/部分 usage；SSE message_start 后多次累计 output_tokens（例如 1、4、9 最终为 9）、跨字节分片、重复统计更新、取消、断流、错误事件均有反例。
- 全未知显示未知，混合记录显示已知合计与未知请求数；不把 Count Tokens、Models、健康检查或管理员测试累计为推理 Token。
- 正常关闭重启和意外退出恢复均验证；模拟数据库忙/不可写时确认不静默漏记，起始写入失败不会发送上游请求。
- 固定时钟验证 40 天前一刻、正好 40 天、40 天内；服务停机超过清理间隔后启动仍能清理，运行期清理及查询窗口正确，夏令时/本地日期不改变 UTC 边界。
- 复跑前置单相关回归，提供数据库夹具、浏览器步骤、完整测试输出、提交标识和可独立复现的统计/清理反例。

本单复用第 2 单的账户/API 直接配置；双模式都须验证使用者归属和未知用量行为。
