1. 解决什么问题？第一家真实上游的原生客户端可调用，但网页诊断返回 400，阻断候选激活。
2. 依据是什么？当前任务书、最新验收整改要求及上述三条台账；两家已提供的 API 材料均须实际复测。

4. 范围是什么？定位诊断和原生客户端的请求差异，修复网页检测、激活及转发；保留单上游及 Anthropic Messages 合同。
5. 每项压在哪个现有机制上？请求构造和认证复用 UpstreamConnection；诊断判定扩展 UpstreamProbe；地址、认证和凭据沿用 UpstreamOptions/UpstreamService 的不可变候选和版本事务；秘密复用 WindowsSecrets DPAPI；网页复用现有 Razor 表单和 CSRF；版本切换、个人鉴权与流式转发沿用 UpstreamPool/RelayServer；回归扩展现有独立测试工程及浏览器脚本。
6. 如何关联？候选和检测按候选主键关联，活动配置按版本关联；领航员记录仅通过命令主键关联。
7. 怎样读取真实材料？只读取本项目预检结果指向的专用临时目录及 DPAPI 列，解密值仅在进程内使用，不读取或修改 MyCoAI 工作账户。
8. 如何定位？在隔离目录运行当前原生客户端，捕获专用短提示的请求结构，在同一地址、凭据、模型和代理下受控比较；只保存非秘密差异及安全结果。
9. 怎样控制失败？生成请求仍只发送一次，不用目录成功代替调用成功，不改数据库激活标记，不放松 TLS 或重定向检查。
10. 如何保护秘密？真实凭据不进源码、日志和截图；进程输出只提取状态、模型、用量和必要错误，测试使用独立个人令牌。
11. 怎样验证？有针对性的真实差异回归、Release 构建及完整测试；两家网页保存/检测/激活、JSON/SSE、原生工具会话、切换及重启后调用；记录客户端版本。
12. 怎样交付？更新旧的缺少 API 材料表述，保存脱敏证据与完整测试输出，提交修复，记录结果后交回待验收。公网可信 HTTPS 和真实账户 OAuth 缺少的条件继续如实列出。
