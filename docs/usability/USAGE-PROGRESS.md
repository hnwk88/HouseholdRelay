## 动手前十二问

已读取现有三条台账全文和当前任务书、最新批示；台账没有另附十二问模板，以下逐项记录实施依据。

1. 解决什么问题？个人调用尚无跨重启的用量归属、查询及过期清理，不能从进程内完成次数推算消耗。
2. 依据是什么？当前任务书和用量合同；最新批示要求先交付现有 API 的私人试用版本，账户分支以模拟验证。
3. 前置满足吗？基础与上游接入均已验收，当前唯一待实施任务已认领并进入实施中，代码基线 a8b65cb。
4. 范围是什么？个人请求持久化、JSON/SSE 用量、管理员和个人查询、UTC 滚动 40 天清理；保持单上游和现有认证、转发协议。
5. 每项压在哪个现有机制上？身份复用 IdentityService/ClientRegistry 的 user_id 和 token_id；配置版本来自 UpstreamPool 租约；记录和索引扩展 RelayDatabase 的事务迁移；采集接入 UpstreamResponses 的有界 JSON/逐事件 SSE；开始与结束接入 RelayServer；管理查询复用 Razor、管理 Cookie 和 CSRF；个人入口复用个人令牌验证；维护挂在现有应用生命周期；验证扩展独立测试工程和 Playwright 脚本。
6. 怎样关联？每次请求分配唯一 request_id，关联使用者和令牌主键、上游版本；改名或轮换不改历史归属，领航员关联只通过命令主键。
7. 怎样处理缺失？Token 可空，累计事件只更新；区分完整、部分、未提供、不适用；展示已知合计及缺失数，全部未知不显示零。
8. 怎样限制存储和内存？不存请求/回答/凭据；复用有界事件解析，窗口索引、分页、批量删除和短事务；不在网络请求期间持有事务。
9. 怎样处理失败？起始保存失败就拒绝转发；结束保存不受客户端取消影响，有界重试并报告失败；启动将未完成记录恢复为中断，保留已知字段。
10. 怎样守住查询边界？管理员可筛选全部使用者；个人只从有效令牌推导身份，不接收其他人的 ID，不把令牌写入 URL、浏览器存储或日志。
11. 怎样验证？固定时钟、双人并发与双模式、累计/缺失/分片/取消/错误、轮换改名停用、数据库锁与不可写、正常和异常重启、清理边界与查询计划；完整 Release 回归及真实浏览器验证。
12. 怎样交付？保存完整输出、数据库夹具说明、浏览器步骤和脱敏证据，提交本次改动并记录标识，追加结果后交回待验收。
