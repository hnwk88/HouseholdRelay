# 结论：HouseholdRelay

## 结论

**接用**

## 理由

- 选这条路的理由：
  - 骨架是对的。四层分开，项目引用方向是正的，Core 不引用任何项目；表结构每版一个类、一个事务，并有注入故障的回滚用例。
  - 难做对的部分已经做对了：
    - 秘密保护：转发头剔除下游凭据，响应三种编码形式都脱敏，明文用完清零；
    - 出站地址：先解析，全部地址都在允许范围才连，不跟随跳转；
    - 用量记账：未知不写零，金额分币种分来源，不相加；
    - 上游切换：按版本原子切换，在途请求继续用旧连接；
    - 管理入口：只绑回环，防 DNS 重绑定，按页面身份限速；
    - 乐观并发：大部分写入带版本号。
  - 评估范围内的测试 132 条全部通过，编译 0 警告。
- 没选另一条路的理由：
  - 131 条问题里结构性只有 7 条，都落在单个文件或单个方法里：
    - `RelayServer.Handle` 的编排；
    - 仓储里的业务判据；
    - 字符串状态；
    - 主键与外键；
    - 同步检测没有任务。
  - 这些都能在现有项目划分里改，不用动层次和项目间的契约。
  - 工程规模小（src 约 1.1 万行，其中一半以上和官方账户分支混在一起）。重做要连带重写官方账户分支，而那一块不在评估范围，由负责人自己负责，重做反而会把它卷进来。

## 判断依据

- 架构能不能承住后面要加的东西：能。把编排搬进应用服务、仓储只留存取、状态改成封闭枚举之后，以后加一种上游状态或转发策略，只改应用层一处。
- 问题清单里有多少条是改得动的、多少条是结构性的：131 条中，局部可改 124 条，结构性 7 条；高 4 条里，2 条是分层、1 条是主键外键、1 条是读屏按钮命名。
- 改到符合标准的工作量，对比重做的工作量：
  - 整改：分五批，前三批（数据、分层、稳定）是主要工作量，后两批是网页读屏和一致性收尾，都是局部改；
  - 重做：要重写转发、用量、上游管理和官方账户分支，还要重新积累现有的 165 条测试；
  - 整改明显更省。
