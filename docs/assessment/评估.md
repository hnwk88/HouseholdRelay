## 概况

- 做什么的：家用中转。自承载的 ASP.NET Core 服务，家里几台电脑上的 Claude Code 等客户端带个人中转令牌连进来，由它转发给配置好的上游，按人记用量，40 天清理；有 Razor Pages 管理页和个人用量页，用私有 CA 签发 HTTPS 证书。使用者上限 8 人，没有用户管理体系，只在负责人自己的公司和家里用。
- 语言与框架：C#／.NET 10（net10.0-windows），ASP.NET Core 加 Razor Pages，SQLite 手写 SQL（Microsoft.Data.Sqlite），少量原生 js；测试是自写的控制台测试程序（不用测试框架），加 Node 写的浏览器旅程脚本。
- 规模（.cs、.cshtml、.js、.cjs、.css，含官方账户分支）：

## 架构

### 分了哪几层、各管什么

Core（领域）→ Application（服务与端口）→ Infrastructure（适配器）→ HouseholdRelay（组合根、中转端点、页面）。项目引用是 Application→Core、Infrastructure→Application 与 Core、HouseholdRelay→三层，方向是正的，Core 不引用任何项目。数据访问是手写 SQL，没有 ORM；每版表结构一个类，在事务里升级。

### 依赖方向

项目引用干净，但有两处越层：

1. 中转编排写在主程序里：`src/HouseholdRelay/Relay/RelayServer.cs:103-312` 的 `Handle` 一个方法里做令牌复核、准入、用量记账、自动切换循环、错误分类和回写，没有落在应用服务（P-002）。主程序和页面还直接用基础设施的静态类 `UpstreamResponses`、具体类 `UsageService.StorageError`、`UpstreamService.MaxImportBytes`（P-035）。
2. 业务判据沉到仓储：候选上游的状态流转、能不能激活、删除前检查、8 人上限、换家后改记单价，都写在仓储的 SQL 和 C# 里（P-003、P-008）。标准门禁「仓储三条」只认 C# 赋值，认不出 SQL 里的状态推进，所以显示通过。

### 对象边界看不看得清

- 值对象和规则大多在 Core，比如用量累加和金额规则（`UsageAccumulator`、`UsageMoneyRules`），边界清楚，测试也直接测它们。
- 看不清的地方：
  - 状态和类别都是字符串字面量，散在各层比较，用 `_ =>` 兜底（P-037、P-049）；
  - 几处依赖做成可选参数，漏登记时静默降级（P-036、P-054）；
  - 「模型名合法」有四套口径（P-005）。
- 主键都是程序生成的 GUID 文本，用量、尝试记录、单价三张表对上游没有外键，删上游会留下孤儿行（P-001、P-009）。

### 能不能承住后面要加的东西

能。问题都落在单个文件或单个方法里，项目划分和层次不用动：

- 把 `RelayServer.Handle` 的编排搬进应用服务；
- 仓储只留存取；
- 状态改成封闭枚举；
- 主键和外键用一版迁移改。

不先收拾的话，以后每加一种上游状态、一种转发策略，都要同时改仓储 SQL、页面和主程序三处。

结构与数据：

2. 业务判据和状态推进写在仓储里：候选状态、能否激活、删除检查、8 人上限（`UpstreamRepository.cs:126-184`、`IdentityRepository.cs:34-37`；P-003、P-008）。
